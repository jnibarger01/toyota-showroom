# RAV4 Asset Provenance

Full history of the 2024 RAV4 Limited 3D asset, from capture to runtime, and an explicit account of
what this asset can and cannot truthfully support. Written because the source delivery is opaque by
default (see below) — every claim here is checked against a file on disk, not against vendor
copy or assumption from the 4Runner's own asset.

## 1. Capture source

`public/renders/rav4-2024/capture-metadata.json` (already in the repo before this integration,
generated by the capture tooling, not authored for this pass) records:

- Source build: `https://www.modsnation.com/builds/7416-2024-toyota-limited` — the same vendor
  (ModsNation) and build-family numbering (`7416-...`) as the 4Runner's
  `modsnation_7416_assets_assembled.glb`, confirming both vehicles come from one vendor pipeline.
- Delivery: a gRPC-Web protobuf response containing a Base64-wrapped **opaque** main payload
  (`rav4_2024_limited_main.base64`, 15,916 bytes) and a separate Base64-wrapped opaque buffers
  payload (`rav4_2024_limited_buffers.base64`, 5,732,972 bytes). The metadata's own `note` field is
  explicit: *"No direct .glb or .gltf URL was delivered. The decoded first Base64 layer is opaque
  rather than JSON or GLB, so a mesh/material inventory cannot be truthfully extracted from the
  delivered bytes alone."* Those two `.base64` files are kept in `public/renders/rav4-2024/` as
  the raw capture record, but they are **not** used as a runtime asset — there is no honest way to
  turn an admittedly-opaque payload into a mesh/material inventory.
- A **separately decoded** pair, `rav4_2024_limited_decoded.gltf` + `rav4_2024_limited_decoded.bin`,
  captured by the metadata's own account "using the site client decoder in the authenticated
  browser session" — i.e. the vendor's own viewer decoded its opaque payload client-side, and that
  decoded output was captured. This is the same shape of provenance the 4Runner's own asset has
  (a vendor-hosted 3D configurator's exported/decoded geometry, not a raw studio export), and it is
  the only artifact in this capture that is independently verifiable: it is standard glTF 2.0 JSON
  with an external `.bin` buffer, openable and inspectable with ordinary glTF tooling with no vendor
  involvement.

## 2. What the decoded file actually contains (verified, not assumed)

Verified directly against `rav4_2024_limited_decoded.gltf` (dumped with `node -e` against the raw
JSON — the same evidence-first approach `docs/INTEGRATION_GUIDE.md` §3 describes for the 4Runner):

- One scene, one root node (`BODY`), one mesh with **10 primitives**, sharing one `.bin` buffer.
- 10 materials, exact names (no `.001`/`.002`/`.004` suffixes, unlike the 4Runner's equivalents):
  `body.carmain`, `metal.chrome`, `glass.windows`, `glass.windows.windshield`,
  `glass.windows.rear.windshield`, `plastik.all`, `glass.light`, `emissive.foglight`,
  `emissive.brakelights`, `emissive.turnsignal`.
- 7 additional nodes, all children of `BODY`, all transform-only (no mesh): `MOUNT_LICENSE_PLATE_FRONT`,
  `MOUNT_LICENSE_PLATE_REAR`, `MOUNT_SOUND_EXHAUST`, `MOUNT_WHEEL_FRONT_LEFT`,
  `MOUNT_WHEEL_FRONT_RIGHT`, `MOUNT_WHEEL_REAR_LEFT`, `MOUNT_WHEEL_REAR_RIGHT`.
- `KHR_draco_mesh_compression` is required and applied to all 10 primitives, plus
  `KHR_materials_clearcoat` and `KHR_materials_emissive_strength` — already compressed, no
  additional Draco pass needed (`scripts/optimize-models.mjs`'s own convention: a `.gltf` with an
  external buffer and no embedded base64 is left as-is, no re-encoding tax to remove).
- Real bounding box of `BODY` (computed directly from the accessor min/max, not estimated):
  x ±1.097 m, y 0.207–1.820 m, z ±2.474 m — a body roughly 4.95 m long, 2.19 m wide, 1.61 m tall,
  consistent with a real RAV4's dimensions.
- The four `MOUNT_WHEEL_*` translations are numerically identical to the 4Runner's own wheel mounts
  (same rig convention, same vendor tooling — not the same vehicle geometry).

There is **no wheel mesh, no tire mesh, no interior geometry, no separate door, mirror, badge, or
grille node** anywhere in this file. This is a body-shell-only capture, the same category of gap
`docs/INTEGRATION_GUIDE.md` documents for the 4Runner's own asset before its wheel/tire/accessory
geometry was added as a later, separate delivery.

## 3. What shipped as the production asset, and why

`public/models/rav4-2024/rav4_2024_limited_decoded.glb` is the decoded capture, copied into the
runtime asset convention (`public/models/<vehicle>/...`) and then run through
`scripts/optimize-models.mjs` — the same pipeline every other vehicle's GLB in this catalog goes
through, not a bespoke step for this one. `dedup`/`prune` dropped 8 accessors the source `.gltf`
carried but nothing referenced, and `draco({ method: "edgebreaker" })` re-applied the identical
codec the source already used (`KHR_draco_mesh_compression` — not a codec swap, not a Meshopt
adoption); node names, material names, and all ten primitives are unchanged, verified directly
against the output (§2's node/material list matches exactly). The result is a single binary `.glb`
at 504,280 bytes (~0.48 MiB), down from the source pair's combined ~3.24 MiB, satisfying
`tests/canvasOrdering.test.ts`'s "ships every runtime model as .glb" invariant — a `.gltf` with an
external `.bin` sibling costs the running app an extra network round trip before it can start
decoding geometry, which is exactly the shape that invariant exists to catch.

The original decoded `.gltf`+`.bin` pair is untouched at `public/renders/rav4-2024/` — the
reference/captured copy this section describes — while `public/models/rav4-2024/` holds only the
optimized, runtime-ready `.glb`. `optimize-models.mjs` deletes the intermediate `.gltf` it rewrites
from (the same behavior it already has for the 4Runner's tire/wheel assets); its external `.bin`
sibling became orphaned by the rewrite and was removed by hand for the same reason.

It qualifies as "sufficiently valid for runtime use" on these grounds:

- It is standard, spec-compliant glTF 2.0 — successfully parsed by `@gltf-transform/core`'s
  `NodeIO` and by the same `GLTFLoader` path every other vehicle in this catalog uses.
- It is complete for what it actually is: a body shell, not a partial or corrupted capture of a
  fuller vehicle. Nothing in it is truncated, and no accessor or bufferView is malformed.
- Every semantic claim made about it (§2 above) is independently checked against the file, not
  taken from the vendor.

What it is **not**, and what this integration deliberately does not pretend it is:

- Not a full production vehicle capture with wheels, interior, doors, mirrors, or a badge.
- Not re-encoded with a different compression scheme — Draco in, Draco out, same settings the
  optimizer already uses for every other vehicle.

## 4. Scene identity and the truthful gap

`lib/data/sceneMap/rav4.ts` declares scene identity only for what is real: `body.exterior` (paint),
`body.trim.chrome`, `body.trim.plastic`, three glass regions, and four light regions — ten
`material-region` entries, all against `BODY`'s real material slots (confirmed by
`npx tsx scripts/asset-pipeline-report.ts`: "RAV4 body: 10 parts satisfied, 0 unexpected
violations"). Wheels, tires, doors, mirrors,
badge, grille, roof, and interior are forward-declared against node names that do **not** exist in
this file (e.g. `WHEEL_MESH_FRONT_LEFT`, deliberately distinct from the real but geometry-less
`MOUNT_WHEEL_FRONT_LEFT`), so `buildSceneRegistry` reports them unsatisfied instead of either
throwing or — worse — registering a "wheel" against an empty transform node and reporting it
satisfied when nothing is there to click or highlight.

`lib/data/vehicles/rav4.ts`'s `threeDConfig.wheelMountNames` still lists the four real
`MOUNT_WHEEL_*` nodes — they are real attachment points, and exposing them costs nothing and saves a
future wheel-asset delivery from needing a data-model change, exactly the role
`docs/INTEGRATION_GUIDE.md` §1 describes for the 4Runner's own wheel assets having arrived as a
separate, later delivery.

`lib/data/options/rav4.ts` therefore ships only paint (targeting `body.carmain`) and a chrome-trim
finish (targeting `metal.chrome`) — the only two customizable slots this geometry actually supports.
There is no wheel-swap, tire-letter, or interior-material catalog for this vehicle, because there is
no real geometry for any of those operations to target.

## 5. Precise blocker for a "full" RAV4

If a complete RAV4 (wheels, interior, doors, mirrors, badge) is wanted later, the blocker is
external and specific: **the vendor delivery for this build never exposed a decodable payload
containing that geometry** — the only decodable artifact captured is the body-shell-only pair this
integration ships. Obtaining fuller geometry requires either a new capture from ModsNation with a
build that includes those parts, or a different source entirely. This is not a processing,
compression, or contract-authoring gap on this repository's side — it is a gap in what was ever
captured.
